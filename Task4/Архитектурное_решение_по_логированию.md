# Архитектурное решение по логированию

## 1. Анализ системы

Логирование необходимо настроить для компонентов, участвующих в обработке заказа:

- Shop API
- MES API
- CRM API
- Messages Queue (RabbitMQ)

Ошибки работы с Shop DB, MES db и 3d files storage на первом этапе фиксируются в application logs соответствующих API.

Диаграмма:

- [task4_jewelry_c4_model_logging.drawio](./task4_jewelry_c4_model_logging.drawio)

На C4-диаграмме источники логов `Shop API`, `MES API`, `CRM API` и `Messages Queue` отмечены отдельным цветом. Добавлена цепочка централизованного сбора и анализа логов.

### INFO-логи

| Событие                               | Что логируем                                                               |
|---------------------------------------|----------------------------------------------------------------------------|
| Создание заказа                       | `timestamp`, `order_id`, `customer_id`, `trace_id`                         |
| Загрузка 3D-модели                    | `timestamp`, `order_id`, `file_id`, `trace_id`                             |
| Приём B2B API-запроса                 | `timestamp`, `client_id`, `request_id`, `endpoint`, `order_id`, `trace_id` |
| Начало расчёта стоимости              | `timestamp`, `order_id`, `trace_id`                                        |
| Завершение расчёта стоимости          | `timestamp`, `order_id`, `duration`, `result`, `trace_id`                  |
| Изменение статуса заказа              | `timestamp`, `order_id`, `old_status`, `new_status`, `trace_id`            |
| Отправка сообщения в RabbitMQ         | `timestamp`, `message_id`, `order_id`, `queue`, `trace_id`                 |
| Успешная обработка сообщения RabbitMQ | `timestamp`, `message_id`, `order_id`, `queue`, `trace_id`                 |

Персональные данные без необходимости в логи не записываются.

### Другие уровни логирования

Дополнительно используются:

- **WARN** — повторные попытки, временная недоступность зависимости и другие нестандартные, но обрабатываемые ситуации;
- **ERROR** — операция завершилась ошибкой: не удалось обработать заказ, обратиться к зависимости или обработать сообщение RabbitMQ;
- **DEBUG** — временно для детальной диагностики конкретной проблемы. Постоянно в production не включается.

## 2. Мотивация

Сейчас команда восстанавливает произошедшее со слов клиента. Централизованное логирование позволит найти события конкретного заказа по `order_id`, связать их с трейсом по `trace_id` и определить сервис и операцию, где возникла проблема.

Это сократит время расследования и снизит нагрузку на поддержку.

### Метрики, на которые повлияет решение

- среднее время поиска причины проблемы
- среднее время устранения проблемы
- количество зависших или задержанных заказов
- количество обращений клиентов по проблемам обработки заказов
- доля проблем, обнаруженных до обращения клиента

### Приоритет внедрения логирования и трейсинга

В первую очередь:

```text
MES API → RabbitMQ → CRM API
```

MES является основным узким местом системы, а RabbitMQ и CRM API находятся на критическом пути дальнейшей обработки заказа.

Во вторую очередь:

```text
Shop API → Shop DB

Shop API → 3d files storage
```

Чтобы покрыть начальные этапы жизненного цикла заказа и диагностировать проблемы при работе с данными заказа и 3D-файлами.

## 3. Предлагаемое решение

Для централизованного сбора, хранения и анализа логов предлагается использовать ELK-стек:

```text
Filebeat → Logstash → Elasticsearch → Kibana
```

- **Filebeat** собирает логи и передаёт их в Logstash
- **Logstash** обрабатывает и нормализует записи
- **Elasticsearch** хранит и индексирует логи
- **Kibana** используется для поиска, анализа и визуализации

Shop API, MES API и CRM API дорабатываются для записи application logs в структурированном JSON-формате. В записи добавляются `order_id` и `trace_id`, чтобы связывать события одного заказа и сопоставлять логи с трейсингом.

На C4-диаграмме добавлены `Filebeat`, `Logstash`, `Elasticsearch` и `Kibana`, а источники логов связаны с Filebeat.

### Безопасность

В логах не сохраняются:

- пароли и токены
- `Authorization` headers и cookies
- содержимое 3D-файлов
- платёжные данные
- персональные данные, которые не нужны для расследования

Если диагностически важное поле может содержать чувствительное значение, оно маскируется перед индексацией.

Доступ к логам:

- support — чтение логов для разбора обращений
- developers — чтение для расследования ошибок
- administrators/SRE — настройка сбора логов, индексов и политики хранения

Kibana и Elasticsearch доступны только из внутренней сети с аутентификацией и разграничением прав.

### Политика хранения

Для каждой системы создаются отдельные индексы:

```text
shop-api-logs-*
mes-api-logs-*
crm-api-logs-*
rabbitmq-logs-*
```

Начальная политика:

- application logs — **30 дней**
- security logs — **90 дней**
- rollover выполняется при достижении индексом примерно **30 GB** или по времени
- старые индексы автоматически удаляются по настроенной политике хранения

Размер и сроки хранения уточняются после накопления статистики реального объёма логов.

## 4. Анализ логов, алертинг и аномалии

Настраиваются алерты на:

- резкий рост количества `ERROR`
- повторяющиеся ошибки обработки сообщений RabbitMQ
- рост ошибок внешнего B2B API
- отсутствие ожидаемого изменения статуса заказа в течение допустимого времени

Также необходимо отслеживать аномалии. Например, резкий рост количества создаваемых заказов или запросов одного B2B-клиента может означать ошибку клиента или DDoS-атаку.

На первом этапе достаточно пороговых правил. После накопления статистики можно добавить автоматический поиск отклонений от обычного поведения.

| Поиск по логам         | Полнотекстовый и структурированный поиск                      | Полнотекстовый и структурированный поиск        | Полнотекстовый поиск и развитая аналитика   |
| Визуализация           | Kibana                                                        | OpenSearch Dashboards                           | Собственные dashboards                      |
| Алертинг               | Поддерживается                                                | Поддерживается                                  | Поддерживается                              |
| Масштабирование        | Горизонтальное, требуется эксплуатация кластера               | Горизонтальное, требуется эксплуатация кластера | Поддерживает распределённое масштабирование |
| Сбор и обработка логов | Filebeat + Logstash                                           | Data Prepper и другие средства сбора данных     | Собственные агенты и средства обработки     |

### Выбор

Для проекта выбирается **ELK**.

Плюсы:

- единая цепочка сбора, обработки, хранения и визуализации логов
- быстрый поиск по структурированным данным
- поддержка отдельных индексов и политики их жизненного цикла
- подходит для централизованного анализа логов нескольких сервисов

Минусы:

- Elasticsearch требует дополнительных ресурсов и эксплуатации кластера
- лицензия менее свободная, чем Apache 2.0 у OpenSearch

OpenSearch является близкой альтернативой с более свободной лицензией, но для поставленной задачи ELK уже предоставляет весь необходимый набор возможностей.
