# Планирование: анализ, идентификация проблем и поиск решений

## 1. Проблемы текущей архитектуры

### 1.1. Нет сквозной наблюдаемости заказов

Жизненный цикл заказа распределён между Internet Shop, MES и CRM. Сейчас нельзя быстро определить, где находится конкретный заказ, сколько времени он находится в текущем статусе и на каком этапе возникла задержка.

### 1.2. MES является потенциальным узким местом

Один экземпляр MES API одновременно:

- обслуживает запросы MES, которым пользуются операторы
- принимает запросы внешнего API
- рассчитывает стоимость изделий
- работает с MES DB
- взаимодействует с RabbitMQ

После открытия внешнего API нагрузка на MES значительно выросла.

### 1.3. Расчёт стоимости является длительной операцией

Расчёт занимает в среднем 2–3 минуты, а для сложных моделей — до 30 минут. При росте количества одновременных расчётов они могут занимать значительную часть ресурсов MES и замедлять обработку остальных запросов.

### 1.4. Внешняя нагрузка не контролируется

После открытия внешнего API нагрузка резко выросла. В текущей архитектуре не описаны механизмы ограничения и регулирования входящего потока запросов, поэтому внешние клиенты потенциально могут перегрузить MES.

### 1.5. Надёжность обмена сообщениями через RabbitMQ требует проверки

MES и CRM обмениваются информацией через RabbitMQ. Из условия нельзя определить надёжность обработки сообщений, поэтому необходимо проверить механизмы повторной обработки, DLQ, идемпотентность и мониторинг очередей.

### 1.6. Медленно работает список заказов в MES

Фильтрация по статусам и пагинация не решили проблему загрузки первой страницы. Необходимо проверить запросы к MES DB, планы выполнения, индексы, сортировку и фактическую нагрузку на БД.

### 1.7. Ограниченные возможности масштабирования

Каждое приложение работает в одном экземпляре, а БД обслуживают операции чтения и записи одним экземпляром. Такая архитектура ограничивает возможности масштабирования и повышает влияние отказа отдельного компонента на работу системы.

### 1.8. Ручное тестирование замедляет выпуск релизов

Критические E2E-сценарии проверяются вручную одним QA-инженером. При обнаружении ошибок выпуск блокируется до их исправления, а время подготовки релиза продолжает увеличиваться.

## 2. Инициативы

### 2.1. Внедрить сквозную наблюдаемость заказов

Настроить мониторинг, централизованное логирование и трейсинг. По заказу должна быть возможность определить его текущий статус, историю переходов и место возникновения задержки.

### 2.2. Перевести расчёт стоимости на асинхронную обработку

MES API принимает запрос и помещает задание на расчёт в очередь. Расчёт выполняется отдельными обработчиками, количество которых можно увеличивать независимо от MES API.

### 2.3. Управлять нагрузкой внешнего API

Для внешнего B2B API необходимо предусмотреть механизмы управления нагрузкой:

- rate limiting для защиты от резких всплесков запросов;
- ограничение количества одновременно выполняемых расчётов;
- backpressure при перегрузке системы.

Это позволит принимать растущий поток заказов контролируемо и не допускать деградации MES.

### 2.4. Повысить надёжность RabbitMQ-интеграции

Проверить и при необходимости настроить retry, DLQ, идемпотентную обработку сообщений, мониторинг состояния очередей и обработку ошибок.

### 2.5. Оптимизировать список заказов в MES

Провести профилирование запросов первой страницы MES и на основании результатов оптимизировать запросы и индексы. Дополнительные способы оптимизации выбирать после анализа фактической нагрузки.

### 2.6. Обеспечить масштабирование критичных компонентов

Подготовить MES к горизонтальному масштабированию. MES API и процессы расчёта стоимости должны масштабироваться независимо друг от друга.

### 2.7. Автоматизировать критические E2E-сценарии

В первую очередь автоматизировать основной жизненный цикл заказа:

`INITIATED → FILE_UPLOADED → SUBMITTED → PRICE_CALCULATED → MANUFACTURING_APPROVED → MANUFACTURING_STARTED → MANUFACTURING_COMPLETED → PACKAGING → SHIPPED → CLOSED`.

## 3. Приоритет инициатив

| Приоритет | Инициатива                            | Причина                                                           |
|-----------|---------------------------------------|-------------------------------------------------------------------|
| 1         | Сквозная наблюдаемость заказов        | Сейчас неизвестно, где именно возникают задержки                  |
| 2         | Асинхронный расчёт стоимости          | Длительные расчёты замедляют обработку остальных запросов MES API |
| 3         | Управление нагрузкой внешнего API     | После открытия API количество проблем резко выросло               |
| 4         | Надёжность RabbitMQ                   | От обработки сообщений зависит переход заказа между MES и CRM     |
| 5         | Оптимизация MES dashboard             | Медленная выдача мешает операторам брать новые заказы             |
| 6         | Масштабирование критичных компонентов | Необходимо для дальнейшего роста нагрузки                         |
| 7         | Автоматизация E2E                     | Ускорит выпуск изменений и снизит риск регрессии                  |

Сначала необходимо получить возможность находить место задержки заказа.

Затем — отделить длительные расчёты от основного потока обработки запросов MES API и сделать внешний поток управляемым. 

После стабилизации основного процесса можно улучшать производительность, масштабируемость и процесс выпуска изменений.

## 4. Целевая архитектура через полгода

Через полгода Internet Shop, CRM и MES остаются отдельными приложениями, но архитектура становится наблюдаемой, управляемой по нагрузке и масштабируемой.

Основные изменения:

- для ключевых компонентов настроены мониторинг, централизованное логирование и трейсинг
- длительный расчёт стоимости вынесен из основного потока обработки запросов MES API и выполняется асинхронно через очередь
- нагрузка внешнего API контролируется и регулируется
- для RabbitMQ настроены обработка ошибок и мониторинг очередей
- MES может горизонтально масштабироваться
- получение новых заказов операторами оптимизировано
- критические E2E-сценарии автоматизированы

Целевая архитектура отражена на доработанной C4-диаграмме:

## 5. Три инициативы на ближайшие полгода

### 1. Сквозная наблюдаемость заказов

Позволит определить реальные причины задержек и находить зависшие заказы до появления жалоб клиентов.

### 2. Асинхронный расчёт стоимости

Отделит расчёты продолжительностью до 30 минут от основного потока обработки запросов MES API и позволит масштабировать вычисления независимо.

### 3. Управление нагрузкой внешнего API

Позволит согласовать входящий поток запросов с возможностями системы и не допускать перегрузки MES.

Эти инициативы последовательно позволяют:

1. определить причины задержек;
2. разгрузить основной MES;
3. защитить систему от повторной перегрузки.
