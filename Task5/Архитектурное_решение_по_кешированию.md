# Архитектурное решение по кешированию

## 1. Анализ системы

Кеширование имеет смысл применить к **чтению списка заказов в MES**.

Причины:

- операторы регулярно открывают один и тот же список заказов
- первая страница списка загружается медленно
- повторные запросы создают нагрузку на MES DB

Расчёт стоимости и изменение статуса заказа не кешируются: это операции, для которых важны актуальные данные и запись в основной источник.

---

## 2. Мотивация

Серверное кеширование списка заказов должно:

- уменьшить время загрузки страницы MES
- сократить количество повторных запросов к MES DB
- снизить нагрузку на MES DB
- ускорить работу операторов со списком заказов

Кеширование не заменяет профилирование запросов и оптимизацию БД. Оно используется для повторяющихся операций чтения.

---

## 3. Предлагаемое решение

Для списка заказов используется **серверное кеширование в Redis**.

Клиентское кеширование не выбирается, поскольку список заказов общий для нескольких операторов и его состояние изменяется. Серверный кеш позволяет централизованно управлять актуальностью данных.

### Выбор паттерна кеширования

Для работы с кешем используется **Cache-Aside**:

1. MES API получает запрос списка заказов.
2. MES API проверяет Redis.
3. При `cache hit` данные возвращаются из Redis.
4. При `cache miss` MES API получает список из MES DB.
5. Результат сохраняется в Redis и возвращается клиенту.

Ключ кеша должен учитывать параметры, влияющие на результат запроса. Например, для списка с фильтрацией по статусу:

```text
mes:orders:list:{status}:{page}:{sort}
```

| Паттерн           | Решение                                                                                                                                        |
|-------------------|------------------------------------------------------------------------------------------------------------------------------------------------|
| **Cache-Aside**   | Выбран: подходит для повторяющихся операций чтения и позволяет обратиться к MES DB при недоступности кеша                                      |
| **Write-Through** | Не выбран: требует синхронного обновления кеша при каждой записи, тогда как кеширование нужно прежде всего для ускорения чтения списка заказов |
| **Refresh-Ahead** | Не выбран: требует фонового обновления и создаёт дополнительные обращения к БД даже для невостребованных данных                                |

### Инвалидация кеша

Основная стратегия — **инвалидация по ключу при изменении данных**.

После того как новый статус сохранён в MES DB, MES API удаляет из Redis затронутые кешированные списки. Следующий запрос получает актуальные данные из MES DB и заново сохраняет их в кеш.

Дополнительно для ключей задаётся **TTL 60 секунд** как страховочный механизм на случай, если программная инвалидация не сработает.

| Стратегия                                     | Оценка                                                                                                                                 |
|-----------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------|
| **Инвалидация по ключу при изменении данных** | **Выбрана:** после изменения заказа MES API удаляет затронутые ключи, поэтому следующий запрос получает актуальные данные              |
| **Временная инвалидация (TTL)**               | Используется дополнительно как страховка, но не как основная стратегия: до истечения TTL пользователь может получить устаревший список |
| **Инвалидация по запросу**                    | Не выбрана: проверка или очистка кеша при каждом чтении снижает эффект от кеширования                                                  |
| **Полная очистка кеша**                       | Не выбрана: удаляет в том числе данные, которых изменение заказа не затронуло, и увеличивает количество последующих обращений к MES DB |

TTL и набор кешируемых запросов необходимо уточнить после получения метрик реальной нагрузки.

### Сравнение вариантов решения

Рассмотрены два варианта серверного кеширования списка заказов в Redis.

|              | Решение 1: Cache-Aside                                                                                              | Решение 2: Refresh-Ahead                                                                                                  |
|--------------|---------------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------|
| **Описание** | MES API обращается к Redis. При `cache miss` получает данные из MES DB и сохраняет их в кеш                         | Популярные списки заказов обновляются в Redis заранее, до истечения TTL                                                   |
| **Плюсы**    | Простая реализация; кешируются только реально запрошенные данные; при недоступности Redis можно обратиться к MES DB | Меньше `cache miss`; часто используемые данные уже находятся в кеше                                                       |
| **Минусы**   | Первый запрос после инвалидации обращается к MES DB                                                                 | Нужен механизм фонового обновления; создаётся дополнительная нагрузка на MES DB; необходимо определять популярные запросы |

Для текущей системы выбирается **Cache-Aside**. Он проще в реализации, не создаёт постоянной фоновой нагрузки на MES DB и кеширует только действительно востребованные данные.

**Refresh-Ahead** можно рассмотреть позже, если мониторинг покажет большое количество повторных `cache miss` для одних и тех же запросов.
